封面说明

本方案在 DsToolKit 现有 Web+后端（Node.js/Express/Prisma/MySQL）基础上，新增三大客户端能力：Flutter 移动端（iOS/Android）、DsToolKit MV3 浏览器扩展、DsToolKit Extended 油猴脚本。三者通过 OAuth2 + RESTful API（dstk_ 令牌）与后端通信，底层以类 Git 的内容哈希 + diff-match-patch 实现对话数据的无感增量同步。

OAuth2 + RESTful API · 双轨 Token 体系

两种颁发路径，
同一校验入口。

双轨 Token

  • 轨 1 · Web JWT（现有不变）：Vue 应用登录用，/api/auth/* 签发，Bearer <jwt>，verifyJwt
  • 轨 2 · dstk_ RESTful Token（扩展）：
    • a) Web 手动创建（/api/tokens POST）← 现有
    • b) OAuth2 授权码 → 后端内部创建 ApiToken 行 ← 新增
  • 统一入口 verifyApiToken：SHA-256 比对 → 查等级配额 → lastUsedAt 更新

Scopes 矩阵

read:conversationsGET /api/v1/configs & /conversations/*
write:syncPOST /api/v1/sync/push（插件核心）
searchGET /api/v1/search（Flutter 远端搜索）
offline_access发放 30 天 refresh_token

PKCE 授权码流程（以 Flutter 为例）

①
生成 code_verifier（32B 随机）→ challenge = B64URL(SHA256(v))
②
WebView 打开 /api/oauth/authorize?client_id&code_challenge&S256&redirect_uri=dstoolkit://...
③
用户 Web 登录 → 授权确认页 → 302 回跳 scheme:?code=...
④
App POST /api/oauth/token：grant_type=code + code_verifier
⑤
后端校验 verifier ⇔ challenge，签发 { access(dstk_), refresh, expires_in }
⑥
access 过期走 refresh_token 模式；Web 端可一键吊销
鉴权体系设计意图

为什么 OAuth2 颁发的 Token 最终不另起炉灶而复用 ApiToken 表？因为现有 verifyApiToken 已实现 tier 检查、速率限制、lastUsedAt 统计。保持一条校验链，减少分支。OAuthToken 表额外维护 refresh 关联，使吊销链能从 user → 所有 token（含 Web 手动创建 + OAuth 自动创建）。Public client（App、插件都是 isPublic=true）必须走 PKCE 防代码截取攻击；插件用 chrome.identity API，Flutter 用 custom scheme + Universal Links fallback。

Git 风格同步 · 增量差分协议

不引入真实 Git，
只复用 Git 的思想。

内容哈希 + 父指针链表 + 文本差分 = 轻量可靠的同步协议。

术语映射表

Git 概念DsToolKit 实现
RepositoryUser + DeepseekConfig → SyncHead.headHash
CommitSyncCommit 行：content-based hash + parentHash
Diffdiff-match-patch patch_toText 序列化 JSON
SnapshotSyncCommit.snapshotJson（首次/大变更场景）
ConflictparentHash != HEAD → 409 + 返回缺失链 → 本地 rebase

Patch JSON 操作类型

  • { op: "replace", path, text }：标题/单字段替换
  • { op: "patch", path, dmpText }：文本级差分（最常用，95% 节省）
  • { op: "add", path, value }：新增消息节点（用户发/AI回）
  • { op: "remove", path }：删除节点（用户撤销等）

📉 压缩效果预估

首次全量（~50MB ZIP） gzip + snapshot → ~8MB
单条消息 patch（200字改动） ~250 字节（节省 99%）
编辑一句话 dmp patch ~80B（节省 95%）
为什么不直接用 isomorphic-git？

真实 Git 仓库适合纯文本文件版本管理；我们的底层是结构化 mapping JSON 树 + MySQL 行。直接引入 git 仓库（每次操作要写文件树、创建 packfile、GC）在 MV3 Service Worker（无持久 FS）和 MySQL 存储层都非常别扭。用 Git 的核心思想（内容寻址哈希 + 父指针链 + 差分）比照搬 Git 二进制格式更贴合场景。diff-match-patch 是 Google 出品的久经考验的文本差分库，纯 JS 实现零原生依赖。

📱 平台级原生适配清单

  • OAuth 回跳：
    • Android：intent-filter scheme="dstoolkit" 包名级别
    • iOS：Info.plist CFBundleURLSchemes + Universal Links 备用
  • 存储权限：
    • Android 13+ READ_MEDIA_IMAGES；12- READ_EXTERNAL_STORAGE
    • iOS NSPhotoLibraryUsageDescription；不用 PHPhotoLibrary.full（参考 1149208 经验）
  • 通知：FCM + flutter_local_notifications；冷启动点击跳转对话页

Flutter 方案的经验教训复用

关键经验来自 Experience 1149208 和 1585605：(1) 权限枚举绝不使用不存在的 Permission.photosFullAccess，必须按平台分支（Android storage/photos；iOS photos）且失败原因透出 UI 层；(2) 三方公式渲染库 flutter_math_fork 必须搭配降级渲染策略（catch 失败，展示纯文本/代码块而不是崩溃白屏）；(3) 长耗时链路（AI 摘要/导出）必须显示分步进度：同步中 → 解析 → 渲染。项目结构遵循 Repository + DAO + Riverpod 分层，业务逻辑集中在 Provider 而不是散布在 UI Widget 内，避免页面各处重复状态逻辑。

MV3 关键注意事项

Manifest V3 两大坑：(1) Service Worker 30s 无事件就睡眠，所有状态必须持久化到 chrome.storage 或 IndexedDB，绝不能用模块级变量存；(2) setTimeout 不起作用（SW 睡眠后定时器失效），必须用 chrome.alarms 做定时。断网重试设计：失败请求入 IndexedDB sync_queue，alarm 每分钟批量出队重推（失败指数退避 1/2/4/8 分钟，上限 1 小时）。Extended 与 content_bridge 的 postMessage 用 HMAC 校验：页面每次加载生成随机 salt，Extended 签名时 + 页面会话密钥，避免被其它注入脚本伪造同步 payload（可能上传恶意内容）。

DsToolKit Extended · 油猴捕获策略

三层兜底捕获 + 七个触发时机，做到「每次对话结束无感 commit 同步」。

L1 · DOM Mutation（最稳定）

  • 监听 [data-testid="chat-msgs"] 容器变更
  • 新增消息节点 → 抓取 innerText / data-content
  • 输入框 input + 发送按钮 click → 捕获用户输入
  • 重新生成按钮 click → 标记为新 version

L2 · Fetch/XHR 拦截（最准确）

  • 重写 window.fetch 拦截 /v1/chat/completions

  • 拦截失败自动回退 L1

  • 遍历 __reactFiber / _reactRoot 内部节点

Extended 捕获设计要点

三层兜底设计的本质是容忍官网改版（DeepSeek 随时可能换 DOM class 或 data-testid）。L1 脆弱但快速；L2 准确但依赖 API URL 不变；L3 丑但能扛住 React 组件架构稳定的特性。七个触发时机中，①-④ 是「消息级 patch」，⑤-⑥ 是「会话级 commit」做最终一致性保证，⑦ 是用户主动「立刻同步」按钮（也是注入 UI 的一部分：DeepSeek 页面右上角角标 + 消息悬浮菜单「📌 导出到 DsToolKit」）。注入 UI 注意：不能遮挡官网原生功能，角标固定右上角堆叠，点击只弹浮层（不跳转），保持 DeepSeek 使用体验。
